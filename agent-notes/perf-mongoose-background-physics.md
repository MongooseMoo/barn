## Decisions and why

- Use a disposable checkpoint, the real sound catalog, and a loopback-only Linux network namespace. The dump contains saved background jobs and production service configuration.
- Use Barn's MOO and Go profilers, runtime diagnostics, and conflict census before proposing instrumentation. Keep capture overhead distinct from an eventual speed comparison.
- Measure the original and candidate from identical preserved inputs. The production snapshot has advanced in wall-clock age since the first baseline, so start both processes at the same wall-clock time on separate CPU groups, then swap groups for a second pair. Compare the paired runs with each other.

## Surprises

- Mongoose world source lives in the database. The project hub is a plain directory, and the Ops checkout beside it is a Git repository.
- This checkpoint has no `$sunnet_scheduler` property. `$physics` runs its pending ledger from a single wakeup, and saved task 706611050 runs the separate one-second universe loop on `#4143` through `#1:_every`.
- The original MOO profile included `moo.verb` only. The documented `moo.task` filter returned `TagFocus expression matched no samples` for the known universe task, which did appear in the Go profile. The new profile demonstrated the matching task label on a real universe stack.
- The server said `ready` before the cooperative physics rearm finished. Its startup task was still suspended during shutdown, and the checkpoint writer kept that task in Barn frame form because it could not encode one `#9655:rearm` operand for Toast. Treat the CPU captures as restart load with concurrent recurring physics.

## Implementation plan

1. Add task ID attribution to the existing MOO profile collector so task 706611050 can be followed across Go CPU, MOO wall/ticks, and runtime phases. Keep the default collector's overhead measured against the observed wakeup/fork population. Verify profile samples for two tasks with the same root verb and the same stack can be distinguished.
2. Reduce verb-resolution allocation at `db/store/store_resolve_cache.go:455`. This is insertion and table growth, with 1.48 GiB sampled on the insertion line and about 5 MiB on the cap reset. `respond_to` attributed 533 MiB of 659 MiB to callable resolution, so preserve its visibility and alias results while measuring the shared resolver. Start with the existing transaction memo representation and its measured growth costs. Keep positive and negative selections, local-write behavior, read marks and generation invalidation intact. Run the pinned Elle workflow for any dispatch or property-memo change.
3. Reduce protected builtin activation overhead, starting at `vm/op_verb.go:373`. The second CPU profile credited `pushProtectedVerb` with 5.23 seconds inclusive; the allocation profile assigned 228.91 MiB directly to its argument copy. Preserve wrapper dispatch, immutable argument lifetime, `pass()`, suspension, and permissions. Reuse the existing argument-list path where ownership permits. Measure the common single-argument call shape. Property replay is another independent candidate: `lookupPropMemo` used 8.83 seconds inclusive in the second CPU capture, 5.41 seconds in `replayPropMemo`.
4. Make the single-argument `mapvalues(map)` walk the map in existing Toast order and fill its result values directly. The profile attributed 69.47 MiB of its 77.26 MiB to `Pairs`, which materializes keys the builtin discards. Keep keyed lookup and error semantics. `listdelete` and SQLite are lower priorities based on the measured allocation and phase evidence.
5. Compare an unchanged Barn build and each candidate against identical immutable input hashes and equivalent completed work in separate runs. Report CPU, allocation, completed universe frames, and committed and discarded physics ticks. Record wall-clock deadline effects separately from code savings. Keep uninstrumented CPU comparisons separate from diagnostic runs.

The largest recurring waste is shared Mongoose scheduler state. The world-side cleanup is to reduce whole-ledger and timer updates inside parallel transition workers while preserving due order, stale-entry checks, cancellation, and retry backoff. `fire_transition:26` fetches the whole ledger for a type guard. `arm:9–32` reads and rewrites the ledger and reads the shared timer. `wake:40–44` publishes the ledger and head, and `set_wakeup:22` publishes the replacement timer. In Barn, the assignment to the local map still calls persistent `MapSet` after the property is cleared (`vm/collection_helpers.go:61` and `types/map.go:591`). The other world-side cleanup to investigate is the unconditional `settle_damage` path for each qualifying `$gpo` during startup rearm. Before changing it, check which timestamp, recovery, and scheduling effects healthy objects require. World edits are outside the Barn implementation plan.
