## Design bound to merged code
- Barn: `internal/app/app.go` calls `format.RecoverCheckpoint(cfg.DatabasePath)` inside the `cfg.ProfileManifest != ""` block before `profile.BuildManifest`. Reason it is not moved after LoadDatabase: the manifest must exist before `ReserveListeners` (comment there; moo-conformance-tests `server.py:308-321` waits for the port then `plugin.py:332-339` reads the manifest).
- Lifecycle (`scripts/mongoose_barn_process.py`): `OwnedBarnServer(environment=...)` passes the stop spec env to Popen and records it; the absent-input refusal is dropped; `_validate_profile` requires manifest `database_checksum` == sha256 of `--db` read after readiness (the database recovery selected), and for non-recovered launches also == the pre-launch hash; `_recovered_pair` records `pair_digest` (a missing sidecar is recorded, not raised) so the oracle judges a mixed pair. New: `stop_records(data)`, `wait_stop(boundary, expected, timeout)` (stop record in the live log, then /proc state T), `start_until_stop(expected, timeout)` (recovery-time stop: same pre-launch checks and spawn as `start`, waits for the record instead of the port).
- Campaign (`scripts/jepsen_checkpoint.py`): `--stages LIST` (default none) selects schedule steps from `STAGE_SCHEDULE`; when set, the Jepsen generator runs one short client phase per step, each with one `:stage-crash` nemesis op, then the final graceful checkpoint (no phase1/phase3/live). Generation g is launched with the stop env of the step it will run. `stage_crash()` = first complete `occurrence-1` live checkpoints, request one more, `wait_stop`, then the same classify / SIGKILL / forensic / in-place restart as `checkpoint_crash` (shared helper), recording the boundary record as the actual reached point. A double-crash step's restart first runs `start_until_stop(recovery-database-restored:1)`, kills it, preserves the second artifact set, records `recovery-stop`, then launches normally. Snapshot oracle and obligations of PR C apply unchanged to every stage crash.
- Analysis: `stage_coverage(lifecycle, selected)` per step: requested, reached record (point/occurrence/pid), stopped state, kill exit, frozen stage, expected frozen stage, restart, recovered pair, oracle verdict; missing item = INCOMPLETE; record from another pid or point = INVALID; double crash requires the second frozen set's `expected_recovery` == the first's and the final recovered pair == it (else RECOVERY). A recovered database equal to a permitted cut's database with a different/absent sidecar is reported as CORRECTNESS "mixed pair accepted" (witness `mixed-pair`).
- Controls: `--control NAME` with `BARN_ELLE_FAULT=NAME` set for every generation; findings carry `witness`; the run passes (exit 0, results `control.passed`) only when its designated witness appears. Faults (elle only, `db/format`): `checkpoint-mixed-pair` (recovery keeps a database matching the journal pair but removes the mismatched sidecar instead of restoring) with step database-renamed:1, witness `mixed-pair`; `checkpoint-drop-append` (writer omits the last token of each nonempty `jp*` list property) with step pair-renamed:1, witness `lost-checkpointed-update`; `checkpoint-duplicate-append` (writer repeats it) with step pair-renamed:1, witness `duplicate-token`.

## Schedule (`STAGE_SCHEDULE`)
capture:1, serialize:1, staged:2, journal-published:1, journal-published:2, database-renamed:1, database-renamed:2, pair-renamed:1, double-crash (database-renamed:2 then recovery-database-restored:1).

## Decisions and why
- Reuse PR C's checkpoint-crash path for stage crashes so the snapshot oracle and obligations are identical; only the stop trigger differs (stop record instead of a random delay).
- Lost-update control drops a token in the writer rather than reusing a stale snapshot: one seam in `writeProperties` serves both row controls.
- Stage campaign is its own job in `jepsen.yml` so the fixed campaign's 20 min budget is unchanged.

## CI run 42964137644 (first #748 run): stages job red
- Controls: drop-append and duplicate-append passed with their witnesses (every process `added_environment` BARN_ELLE_FAULT=<control>); mixed-pair missed (froze at both-renamed). The duplicate tokens and the gen-0 Elle rejection the lead saw are the duplicate-append control's expected witness, not a healthy-run defect; the healthy schedule's processes had only BARN_ELLE_CHECKPOINT_STOP.
- Schedule: capture-1, serialize-1, staged-2 froze at the expected stage. Every rename-stage step (journal-published-1/2, database-renamed-1/2, pair-renamed-1, double-crash) froze at `both-renamed`: e.g. gen-003 (journal-published:1) frozen files show output = journal next, temp gone, server.log ends `checkpoint started` then the stop record, no `checkpoint complete`. So the process ran past its stop point before stopping. Double crash then had nothing to restore, so its recovery stop never fired (TimeoutError).
- Cause: `stopSelf` (`internal/isolationprobe/stop_unix.go`) uses `kill(getpid(), SIGSTOP)`, a process-directed signal the kernel may deliver to another thread (signal(7); POSIX kill only guarantees delivery to the sender when no other thread has it unblocked), so the checkpoint goroutine's thread keeps running until the group stop reaches it.
- Fix: on Linux, `tgkill(getpid(), gettid(), SIGSTOP)` with the OS thread locked (`internal/isolationprobe/stop_linux.go`), so the calling thread itself dequeues SIGSTOP on its return from the syscall. Other platforms now refuse the stop at startup (`stop_other.go`, `elle && !linux`) instead of giving an inexact one. Test `TestCheckpointStopNoCodeRunsAfterStop` (25 helper launches; the helper pins its main goroutine to the thread group leader, as in Barn the checkpoint runs off the leader, and writes a marker right after Pause returns): failed on attempt 0 in WSL Linux with the old `kill`, passes `-count=3` with `tgkill`.

## Surprises
- The recovery-time stop fires during LoadDatabase, before the listener, so that launch waits for the stop record instead of readiness.
- PR C's `_recovered_pair` raises on a missing sidecar, so a mixed (database without sidecar) pair failed the launch instead of reaching the oracle.
- PR C's `pending_pairs` admitted the on-disk output as a pending cut even between the two renames, where it is a mixed pair (next database, previous or no sidecar); a recovery that kept it would match a "permitted" cut. Fixed: with a journal present the output counts only when it equals the journal's next pair. Test `WitnessTests.test_a_database_kept_without_its_sidecar_is_a_mixed_pair`.
- The Jepsen workflow is not a required check (branch protection requires only Build & unit tests, MOO conformance suite, Serializable histories and negative control), so the new job does not block merges by itself; changing that is a settings decision for Q.
