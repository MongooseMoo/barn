# Experiment: Lazy allocation of StoreTxn read-tracking maps (B1)

## Hypothesis
`Store.BeginReadOnly` eagerly allocates SEVEN read-tracking maps (plus a runtime
finalizer) for every transaction, but a typical tiny commit-dominated task touches
only one or two of them. On a CPU profile of the commit-dominated concurrent write
path the Go GC (gcBgMarkWorker + gcDrain) was eating ~35% of CPU, with per-task txn
allocation the dominant source. Making the seven read maps lazily allocated
(mirroring the already-lazy seven write-staging maps) should cut per-task
allocations, shrink the GC share, and raise the 32-worker commit-dominated speedup
above the ~1.98-2.04x baseline.

## Single variable
The seven read maps — objects, scalarReads, relationshipReads, propertyReads,
propertyScans, verbReads, verbScans — were changed from eager `make(...)` in
BeginReadOnly to lazy allocation through the existing `lazySet` helper at every
insertion site. Nothing else: finalizer untouched, commit grouping maps untouched,
floor sharding untouched, scheduler untouched.

## Baseline command + result (this machine, parent commit c09bcae, BEFORE change)
    go test -C . ./scheduler -run 'TestConcurrencyCommitDominatedDisjoint$' \
      -count=5 -v -timeout 240s 2>&1 | grep 'workers=32'

32w commit-dominated speedup (5 runs): 2.02, 1.45, 2.41, 2.19, 2.13
  -> average 2.04x ; per-commit ~11.5 us ; HIGHLY noisy (1.45..2.41 spread).
Arith scaling sweep 32w baseline: 3.77x (pool 290.317ms).

## Experiment result (AFTER change, identical commands)
32w commit-dominated speedup (5 runs): 2.04, 1.65, 1.87, 1.90, 1.84
  -> average 1.86x ; per-commit ~10.66 us.
Arith scaling sweep 32w after: 3.72x (pool 288.416ms).

Reading: the headline speedup RATIO is flat-to-slightly-down and well within the
heavy run-to-run noise (the ratio is normalized against a serial baseline measured
fresh each run, which itself varies). The ABSOLUTE per-commit time improved modestly
(~11.5 us -> ~10.66 us). The read path (arith sweep) did NOT regress (290ms -> 288ms,
3.77x -> 3.72x, identical within noise).

## Failure-analysis gate: before/after profile
The headline gate is weak/ambiguous, so a re-profile is required to check whether the
intended bottleneck (GC) actually shrank.

    go test -C . ./scheduler -run 'TestConcurrencyCommitDominatedDisjoint$' \
      -count=3 -timeout 240s -cpuprofile .probes/cpu.prof -o .probes/s.test.exe
    go tool pprof -top -cum -nodecount=25 .probes/s.test.exe .probes/cpu.prof

GC share (gcBgMarkWorker.func2 + gcDrain, cumulative):
  BEFORE ~35%  ->  AFTER 24.31%.
So the GC share DID shrink by ~10 percentage points. The hypothesis about the
bottleneck (eager txn-map allocation feeding GC) is CONFIRMED.

But the GC win did NOT convert into a speedup-gate win because the new dominant
cost is map ITERATION, not allocation:
  - barn/db/store.(*Store).historyFloor           18.23% cum
  - internal/runtime/maps.(*Iter).Next            15.47% FLAT
  - runtime.mapIterNext                           13.81% cum
`pprof -list historyFloor` localizes 290ms (of 330ms) to:
    for ts := range sh.counts {   // store_history_gc.go:75
i.e. iterating the SHARDED readTS floor-registry maps on the commit hot path. That
is the floor-sharding experiment's territory (explicitly out of scope here). With GC
pressure relieved, floor-map iteration is now the binding constraint, so reducing
txn allocations alone cannot move the 32w commit-dominated speedup further until the
floor-iteration cost is addressed.

4. `go test ./scheduler -count=1 -timeout 240s`                     -> ok (10.729s)

## Metric gate
NOT MET as a speedup improvement. 32w commit-dominated speedup did not move clearly
and repeatably above the ~1.98-2.04x baseline (1.86x avg after, within noise). No
read-path regression. The intended bottleneck (GC) measurably shrank (~35% -> 24%),
but a different, now-dominant cost (floor-map iteration in historyFloor) capped the
end-to-end gain.

## Outcome
PARTIAL / MIXED. The change is correct and beneficial on its own terms — it removes
real allocation/GC pressure (GC share 35% -> 24%), does not regress the read path,
and all contracts incl. -race pass — but as an isolated variable it does not deliver
the speedup the gate requires, because floor-registry map iteration is now binding.

## Worker recommendation
INCOMPLETE / recommend HOLD for combination, not standalone promotion. The GC
reduction is real and the diff is clean and low-risk, but the speedup gate is gated
behind the floor-iteration cost. Recommend promoting this only IN COMBINATION with
the floor-iteration experiment (the historyFloor `range sh.counts` hot loop) — alone
it pays for optionality but does not clear the metric bar.
